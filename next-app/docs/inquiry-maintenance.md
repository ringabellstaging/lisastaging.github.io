# Upstash 与询价系统维护手册

代码核对日期：2026-10-14（多伦多时间）。适用于 Oaktime Staging，正式网站为 <https://www.oaktime.ca>。

本文按当前代码说明维护方式；不代表本次已检查生产账号的配额、备份、告警或密钥保管状态。实际套餐和控制台设置需要登录对应账号核对。本文不包含生产密钥或客户资料。

## 给日常负责人的快速说明

- 每天查看 Porkbun 转发到的实际收件邮箱，包括垃圾邮件；这是日常跟进询价的主要入口。
- Upstash 存的是加密的询价副本、发信进度、重试队列和限流计数，不是可直接浏览的客户管理系统，也不是普通缓存。
- 每条询价从首次保存起保留 **30 天**，重试不会重新延长到 30 天。邮件发送完毕后，存储副本仍保留至到期；邮箱里的邮件不会随数据库记录一起删除。
- 发信失败时系统会自动重试。出现 `needs manual delivery review` 必须由维护人员检查，不能一直等下去。
- **不要清空 Redis、随意更换加密密钥或直接恢复旧数据库。** 这些操作可能丢失询价或使已经发送的邮件再次发送。
- 当前要求是不发送测试邮件。日常维护使用只读检查；手动运行重试任务也可能发送真实邮件，不属于只读检查。

## 1. 询价经过哪些服务

```text
客户提交网站表单
  → Vercel /api/inquiries 校验、限流
  → 服务端加密，原子保存到 Upstash 并加入待发送队列
  → Resend 发送团队通知到 info@oaktime.ca
  → Porkbun 按已有转发规则送到实际收件邮箱

若该条询价启用了客户回执：
  → Resend 另发一封确认邮件到客户填写的邮箱

未完成的发送：
  → Vercel Cron 每 15 分钟调用 /api/inquiries/retry
  → 从 Upstash 取到期任务，重试尚未成功的邮件
```

团队通知的 Reply-To 是客户邮箱；客户回执的 Reply-To 是 `INQUIRY_TO`，目前约定为 `info@oaktime.ca`。客户回执由 Resend 直接发给客户，不需要经过 Porkbun 转发。

`info@oaktime.ca` 是转发地址即可，不需要另外购买托管邮箱。网站公开联系方式中的 `Oaktimeinc@gmail.com` 与服务端 `INQUIRY_TO` 分开管理。

网站显示成功，表示询价已保存；代码中的 `teamSent`、`customerSent` 表示 Resend 接口接受了发送请求，**不等于进入最终收件箱**。当前没有把 Resend 的 delivered/bounced 事件同步回数据库，也没有保存其邮件 ID。要核实最终状态，应查看 Resend 邮件记录和实际收件邮箱；Resend 对 `info@oaktime.ca` 显示 delivered，仍需核对转发后的邮箱。

## 2. 配置放在哪里

入口：[Vercel 项目](https://vercel.com/sandys-projects-490f742e/lisastaging-github-io)、[Upstash 控制台](https://console.upstash.com/)、[Resend](https://resend.com/)。Porkbun 只负责现有域名 DNS 和收件转发。

Vercel 项目为 `lisastaging-github-io`，Root Directory 是 `next-app`。以下服务端变量应只连接 **Production**；本地和 Preview 不使用生产数据库或发信凭证。

| 变量                                                  | 用途及维护注意                                                                           |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `SITE_URL`                                            | 正式来源为 `https://www.oaktime.ca`，参与来源校验和 SEO 配置。                           |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN`               | Vercel 的 Upstash 集成提供的 HTTPS REST 地址与读写令牌。                                 |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | 上一行的替代配置；代码分别优先取这两个变量。避免同时留下指向不同数据库的两套变量。       |
| `INQUIRY_ENCRYPTION_KEY`                              | 32 字节随机密钥的标准 Base64 表示，用于加密、认证和生成 HMAC 指纹。必须保留原值。        |
| `RESEND_API_KEY`                                      | 仅用于发送、限定 Oaktime 发信域名的密钥。                                                |
| `INQUIRY_FROM`                                        | 约定 `Oaktime Staging <info@oaktime.ca>`，发信域名须在 Resend 验证。                     |
| `INQUIRY_TO`                                          | 约定 `info@oaktime.ca`，由服务端决定，不接受客户指定团队收件人。                         |
| `INQUIRY_SEND_CONFIRMATION`                           | 只有字符串 `true` 才开启客户回执。开关在新询价保存时固定，后改配置不会改变旧询价的选择。 |
| `CRON_SECRET`                                         | Cron 请求的 Bearer 验证密钥，不是数据库加密密钥。                                        |

`KV_URL`、`REDIS_URL`、只读令牌不用于当前应用。所需 Redis 操作包含写入、计数、队列和 Lua 脚本，因此运行时不能替换为只读令牌。连接走 HTTPS REST，不依赖固定的 Vercel 出站 IP；密钥不应出现在 `NEXT_PUBLIC_*`、Git、日志或聊天中。

修改环境变量后需重新部署 Production，已部署版本不会自动获得新值。修改数据库地址前要确认这是 Oaktime 的专用数据库，不要与无人机网站共享。

DNS 记录说明见 [Resend DNS 配置](oaktime-resend-dns.txt)。为出站验证而配置 Resend 时，不要替换 Porkbun 收件转发使用的根域 MX；只有更换实际收件服务时才另行规划该变更。

## 3. 数据内容、保留期与限流

询价记录包括地址、邮箱、电话、预算及用户填写的其他信息、语言、联系同意；内部还有创建时间、尝试次数、发送状态和请求摘要。营销订阅选择如存在，也会保存同意时间、文案版本、语言、来源和当时展示的文字。

整个记录先使用 AES-256-GCM 加密再写入 Redis；每次保存使用新随机 IV。密文绑定原 Redis 记录键，因此不能把密文直接改名或复制到另一个询价 ID。控制台看到 `version`、`iv`、`tag`、`ciphertext` 是正常现象。

| Redis 键                    | 内容                                                           | 生命周期                                                         |
| --------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| `oaktime:inquiry:<UUID>`    | 加密的完整询价记录                                             | 首次创建后 30 天；后续保存只使用剩余时间。                       |
| `oaktime:pending`           | Sorted Set，成员是询价 UUID，分数是下次可尝试时间（Unix 毫秒） | 队列本身没有 TTL；完成、超过重试上限或发现记录已过期时移除成员。 |
| `oaktime:lock:<UUID>`       | 并发发送锁                                                     | 120 秒超时；正常结束时核对锁令牌后释放。                         |
| `oaktime:rate:ip:<HMAC>`    | IP 限流计数                                                    | 8 次 / 600 秒。                                                  |
| `oaktime:rate:email:<HMAC>` | 同邮箱的新记录请求限流计数                                     | 3 次 / 86400 秒。                                                |
| `oaktime:rate:all`          | 全站新记录请求限流计数                                         | 40 次 / 86400 秒。                                               |

限流窗口从对应键第一次计数开始，不在多伦多午夜重置。计数不等于最终成功收到的询价数：例如全站计数发生在邮箱限流检查之前。已有询价的重复请求仍受 IP 限流。

队列成员、排队时间、记录键、TTL 和计数仍能被持有数据库权限的人看到。应用层加密不保护已被攻破的 Vercel 运行环境、密钥保管处或收件邮箱。

**数据库不是永久通讯录。** 营销同意证据还会写入团队通知邮件；建立邮件名单时须保留该证据并记录后续退订。当前代码只收集选择，不会自动创建 Resend Contacts 或发送推广活动。数据库到期不会自动删除邮箱副本、外部备份或未来的 CRM 记录，分别需要自己的保留策略。

## 4. 自动重试怎样工作

配置在 [`../vercel.json`](../vercel.json)：`*/15 * * * *`，即每小时第 0、15、30、45 分钟的调度，不等于提交后准确等待 15 分钟。调度日志的时区以控制台标注为准。

- 提交时先尝试发送团队通知，成功后才尝试客户回执。
- Cron 每次最多取 **5 个已经到期的任务**。失败后的退避时间按尝试次数增加，上限 1 小时；实际再处理还取决于 Cron 调度和队列积压。
- 同一任务最多进入 **10 次发送尝试**，超过创建后 **23 小时**停止自动发信，并记录 `needs manual delivery review`。这些限制也适用于提交接口触发的发送。
- 团队通知和客户回执分别记录状态，只重试未被记录为成功的部分。
- Resend 幂等键分别为 `oaktime-team-<UUID>`、`oaktime-customer-<UUID>`。其去重窗口为 24 小时，因此不能把旧任务反复重置为新任务。[Resend 官方说明](https://resend.com/docs/dashboard/emails/idempotency-keys)

停止自动重试后，队列成员会被移除，询价密文仍保留至原到期日。因此，**队列为空不代表历史询价全部送达**，必须同时看错误日志。

重试接口返回的 `processed` 是本轮选中的任务数，`delivered` 是代码判定发送完成的任务数；两者不是邮件数量，也不是收件箱送达量。HTTP 200 本身不证明所有邮件送达。

有有效授权的 GET `/api/inquiries/retry` 会处理队列并可能发送真实邮件。不要把它用于 uptime 探测，不要把 `CRON_SECRET` 放进 URL 或工单。无授权请求得到 401 只证明鉴权生效，不能证明数据库或发信正常。[Vercel Cron 维护说明](https://vercel.com/docs/cron-jobs/manage-cron-jobs)

## 5. 日常检查清单

以下是建议的人工频率，不表示已经创建定期提醒或自动告警。

| 频率                     | 检查与动作                                                                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每个工作日               | 查看真实收件邮箱和垃圾邮件；核对客户反映未收到的询价编号。                                                                                                        |
| 每个工作日 / 故障发生时  | 在 Vercel Production 日志筛选 `/api/inquiries`、`/api/inquiries/retry` 和下节列出的日志。工作时间内尽早处理人工复核项，不要等到 30 天过期。                       |
| 每周                     | 看 Cron 是否按计划调用、有无持续的 401/5xx；看待发送队列是否长期积压，并结合 Resend 邮件状态判断。                                                                |
| 每周                     | 在 Upstash 检查命令用量、存储大小、错误和当前套餐；Resend 检查发信额度。免费额度或 Pro 权益以各服务当时账号为准，不能把 Vercel Pro 当作无限数据库或无限发信额度。 |
| 每月                     | 核对账号权限、双重验证、密钥备份是否可取用、Porkbun 转发目的地，以及任何已启用备份的保留和费用。                                                                  |
| 更换密钥 / 域名 / 部署后 | 核对 Production 环境、DNS 和 Cron；先用只读方式检查。需要真实发信验证时另行获得明确授权。                                                                         |

保持 Upstash **Eviction 关闭**：询价是需要保留的数据，不能在容量紧张时被当作缓存提前淘汰。关闭后达到大小限制可能拒绝写入，应处理容量或套餐问题，而不是直接开启淘汰。[Upstash 官方说明](https://upstash.com/docs/redis/features/eviction)

自动付费升级保持关闭，除非业务负责人另行决定。告警应关注：人工复核日志、持续存储或重试失败、Cron 长时间没有运行，以及配额即将用尽。当前应用只输出日志，没有内置告警邮件或管理后台；部署是否另配了平台告警，需要在账号中确认。

## 6. 不发邮件的只读排查

先从客户提供的 `OT-<UUID>` 获取编号，去掉 `OT-` 后才是 Redis/日志使用的 ID。排查记录使用时间和 UUID，不把客户地址、电话或邮箱复制到公开 issue。

在已登录且确认属于 Oaktime 的 Upstash 数据库 Console 中，可以使用以下只读命令。将 `<UUID>` 替换为真实询价 ID，不要直接照抄占位符。

```text
ZCARD oaktime:pending
ZRANGE oaktime:pending 0 9 WITHSCORES
EXISTS oaktime:inquiry:<UUID>
TTL oaktime:inquiry:<UUID>
TTL oaktime:lock:<UUID>
TTL oaktime:rate:all
```

`TTL` 单位是秒；`-2` 表示键不存在，`-1` 表示没有设置到期时间。询价记录正常应有正 TTL，且不超过约 2,592,000 秒；队列本身没有 TTL 是设计如此。单个键不存在不能独自证明客户从未提交，也可能已过期、被删除或查错数据库。

如需统计记录数量，使用增量 `SCAN`，将返回的游标带入下一次调用，直到游标为 `0`；返回键可能重复。避免用 `KEYS *` 扫全库。示例：

```text
SCAN 0 MATCH oaktime:inquiry:* COUNT 100
```

目前没有面向运营人员的解密查看页或恢复命令。确需取回未送达的记录时，由维护人员在受控环境使用原 `INQUIRY_ENCRYPTION_KEY` 和 [`getJob`](../lib/inquiry-store.ts) / [`decryptRecord`](../lib/inquiry-crypto.ts) 读取目标 UUID；不得把解密结果打印到应用日志、聊天或 Git。只读查询不会发送邮件，但仍会消耗 Redis 命令额度。

## 7. 常见故障处理

| 现象                                                    | 先查什么                                                                          | 如何处理                                                                                     |
| ------------------------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 表单返回 503「暂时不可用」                              | Production 变量是否缺失；REST 地址是否 HTTPS；加密密钥格式是否正确                | 修正配置并重新部署。不要伪造成功响应。                                                       |
| 表单返回 503「无法安全保存」                            | Upstash 连通性、读写令牌、额度、数据库是否暂停或误选；也可能是已有记录解密失败    | 核对最后变更；此响应不能保证一定没有记录，不能立即要求客户反复新建询价。                     |
| 返回 429                                                | IP / 邮箱 / 全站限流窗口，是否遭遇异常请求                                        | 等待窗口到期或引导直接联系团队；核实流量后再决定是否修改代码中的额度，不要直接清空所有计数。 |
| 返回 409                                                | 同一个 requestId 对应的内容发生变化                                               | 先确认是否已有询价；这是防止复用同一编号发送不同内容的保护。                                 |
| 提交成功，但团队没收到                                  | 先搜 Resend 的团队收件人和对应时间，再查实际收件邮箱、垃圾邮件及 Porkbun 转发规则 | 已被 Resend 接受的邮件不会因邮箱端问题自动重发；先定位哪一步失败。                           |
| `[inquiry] email pending retry`                         | 对应 UUID 的队列、Resend 认证/额度/域名与接口记录                                 | 修复原因后由正常 Cron 重试；日志里的状态可能是部分成功。                                     |
| `[inquiry] delivery pending` / `[inquiry] retry failed` | Redis 访问、原加密密钥、最近部署及运行时错误                                      | 代码使用泛化错误保护隐私，需要结合平台状态和变更记录定位。                                   |
| `[inquiry] needs manual delivery review`                | 原创建时间、尝试次数、Resend 的实际发送记录、最终邮箱                             | 已停止自动重试；先查明是否送过，再决定人工处理。不能只重新入队或重置次数。                   |
| Cron 401                                                | 调度请求和当前部署的 `CRON_SECRET`                                                | 修正部署/配置；不要移除鉴权。                                                                |
| Cron 200，但持续有积压                                  | 返回计数、任务到期时间、锁和错误日志                                              | 每轮只处理 5 个任务；检查根因及积压，必要时评估调度/批量修改。不要并发反复手动触发。         |
| 有密文但读不出来                                        | 是否换过密钥、是否复制到不同记录键、格式或版本是否损坏                            | 找回原密钥和原记录键；不能靠生成一个新密钥解决。                                             |

如果必须补发，先对照 Resend 与收件邮箱确认缺失的是团队通知还是客户回执，并记录人工处理结果。当前没有人工处理状态后台；任何停止排队或改发送状态的操作需由维护人员针对单个 UUID 执行，并处理好正在运行的任务。不要把已经发过的邮件当作全新询价重建。

## 8. 密钥备份与轮换

至少在公司控制的密码管理器中保存：服务账号及恢复方式、`INQUIRY_ENCRYPTION_KEY`、密钥对应环境/数据库和生效日期。密钥与数据库备份分开授权保管，不写在本文或 `.env.example`。本次文档工作没有导出、读取或备份生产密钥。

| 变更                     | 做法                                                                                                                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Redis 访问令牌           | 更新 Vercel 中实际生效的变量或集成配置，重新部署，核对只读访问和运行日志。撤销旧令牌的时机要兼顾已运行的函数；如已泄露，优先阻断泄露并接受必要的短时维护。无需重新加密记录。 |
| Resend 密钥              | 保持发送权限和 Oaktime 域名范围，更新 Production 后部署，再按处置计划撤销旧钥。待发送任务继续使用原幂等键，不能改成新的询价 ID。                                             |
| `CRON_SECRET`            | 更新 Production 后部署，核对 Cron 鉴权和日志；不影响密文。                                                                                                                   |
| `INQUIRY_ENCRYPTION_KEY` | **不能直接替换。** 当前没有多密钥/keyring 或自动迁移功能。必须保留旧钥，先制定暂停读写/发送、解密并重新加密、保留原 ID/创建时间/剩余 TTL/发送状态的迁移方案。                |

加密密钥也用于请求摘要和 IP/邮箱 HMAC。正式轮换时除了密文，还要迁移或处理摘要校验和限流状态。只改环境变量会导致旧记录解密失败、旧摘要不匹配；新钥不能恢复旧密文。如果旧钥遗失，只能依赖已收到的邮件或其他已授权保存的副本。

调整 `INQUIRY_FROM`、`INQUIRY_TO` 或邮件模板也要检查待发送任务：当前邮件在每次尝试时根据配置/代码重建，同一幂等键的内容变化可能导致提供商拒绝重试或收件人改变。先处理积压，再安排此类变更。

## 9. 数据备份、恢复与迁移

Upstash 的持久存储不能替代独立备份，应用本身没有定时导出或备份任务。控制台提供备份能力，但是否启用、可用性、费用和保留时间须在当前账号确认。不要因写了这份文档就认为每日备份已经配置。[Upstash 备份说明](https://upstash.com/docs/redis/features/backup)

备份应保持加密，保留原记录键、密文、剩余生命周期和发送状态；原加密密钥另存。外部备份不会因为在线 Redis 的 TTL 到期而自动消失，须有清理策略，与对客户说明的保留安排一致。

恢复前必须注意：Upstash 恢复操作会删除目标数据库现有数据。优先恢复到隔离数据库做核对，不直接覆盖生产库。恢复旧快照也可能把已经发过的邮件变回“未发送”，重新接上 Cron 会造成重复发送。

建议由维护人员按以下顺序执行恢复/迁移：

1. 确认受影响时间、备份范围、原密钥可用性，并保留当前生产状态用于比对。
2. 安排维护窗口，同时阻断新的询价提交和自动/人工发送，等待在途请求结束。当前没有维护模式开关；仅关 Cron 不够，因为提交接口也会立即发信，需另行实施受控的维护措施。
3. 在隔离环境恢复，按原 UUID 解密核对。不要连接生产发信凭证或启用调度。
4. 按原 `createdAt + 30 天` 计算剩余 TTL，不把恢复时间当作新创建时间；排除已经过期的记录。
5. 对照恢复后记录、恢复前状态和 Resend 发送记录，逐条确认发送状态。不要恢复旧锁，也不要盲目恢复待发送队列；超过自动处理窗口的任务交由人工复核。
6. 核对密钥、摘要、记录数量、抽样解密及队列后，再切换 Production REST 连接并部署；恢复提交与调度后观察真实流量。最后按保留计划清理迁移副本。

删除单条客户记录时，也要防止待发送任务再次发送或把记录写回；应由维护人员在无该任务并发处理的条件下处理记录和队列，并另外检查邮箱、备份、订阅名单中的副本。当前没有自助删除端点；不要使用全库清空来处理单个客户请求。

## 10. 修改后怎样验证

仅改本文或 README：检查链接、代码中的配置是否与文档一致及 `git diff --check`，无需提交询价或执行生产重试。

修改询价代码时，在隔离环境使用仓库现有检查：

```powershell
Set-Location next-app
npm test
npm run lint
npm run build
```

现有询价测试使用模拟网络，不会发送真实邮件。不要为运行测试把生产密钥下载到本地。Production 核对优先使用只读控制台、日志和现有真实询价记录；任何真实发信测试都不属于上述检查。
